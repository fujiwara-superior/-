## この回答で取っているポジション

### 著作権（5番）

法律上、プログラムの著作権は制作した者に発生し、契約に定めがなければ受託者に留まります
（著作権法第17条・第61条）。したがって藤原の認識は正しいが、**契約書に書かなければ
「聖建様が何の権利で使えるのか」が曖昧**になるため、次の切り分けを明記する。

| 区分 | 対象 | 扱い |
|---|---|---|
| 譲渡 | 教材、画面デザイン、聖建様固有の業務処理、DB設計、蓄積データ | 検収完了かつ代金完済時に移転（27条・28条を含む） |
| 留保 | 本人確認・顔照合・在席確認・視聴整合性の共通モジュール、開発基盤、共通ライブラリ | スペリオルに留保。無償・永続・再許諾不可の利用許諾を付与 |

**27条（翻案権）・28条（二次的著作物の利用権）は、譲渡契約に特掲しないと移転しません**
（著作権法第61条第2項）。譲渡すると決めた以上、書き漏らすと後で揉めます。

### ソースコード（6番）

先方の要求は「進捗確認のため」と明記されている。目的を2つに分解して別々に応じる。

- 進捗の可視化 → **月2回**の進捗報告書 ＋ フェーズごとのデモ ＋ 作業ボードの常時閲覧
- 継続性の担保 → **ソースコードエスクロー**（第三者預託）＋設計書一式の納品

GitHub は「作業管理の部分だけ見せ、プログラム本体は非公開」と平易に説明している。
「工程表は見せるが設計図面の原本は渡さない」という言い方で通す。

**「それでも納品をご希望の場合」の譲歩案は、今回の回答書には載せていない。**
最初から出すとそこが交渉の出発点になるため。先方が食い下がった場合の次の一手として
手元に置いておく（検収完了かつ代金完済後、用途限定・転用禁止を条件に納品）。

### 再委託（11番）

原則は自社開発。ただしサーバー環境の構築など一部で協力会社を使う可能性があるため、
「再委託しません」と言い切らず、**事前報告と承諾を条件に協力会社を使う場合がある**旨を
先に開示してある。責任はすべてスペリオルが負う。

契約書に再委託禁止条項が入る場合は、「事前の書面による承諾を得た場合はこの限りでない」の
併記を求めること。言い切ったあとで外注すると債務不履行になる。

### 意図的に書いていないこと

先方に余計な確認事項を増やさせないため、次を落としてある。

| 落としたもの | 理由 |
|---|---|
| エスクロー預託先の固有名 | 先方が直接その機関へ問い合わせ、契約が遅れるのを避ける。「ご契約後に貴社とご相談のうえ決定」とした |
| 本人確認システム設計書への参照 | 設計書を見せると、そこからさらに確認事項が増える |
| 貴社特別値引きの金額（350,000円） | 金額を出すと値引き自体が交渉の的になる |
| 作業ボードの「期限」表示 | 作業1件ごとに期限を握られると、遅延のたびに追及される。担当者の表示のみとした |
| 協力会社利用時の「事前報告・承諾」 | 都度の承諾取得を自ら義務づけないため。秘密保持と責任の一本化だけ約束する |
| 「貴社発行の契約書に署名する形で差し支えございません」 | 中身を見る前に署名を約束しない |

### 著作者人格権の不行使（5番）

「貴社**および貴社の許諾を受けた者**に対し」ではなく、**「貴社に対し」のみ**とした。
不行使の範囲を最小限にとどめ、交渉の余地を残すため。
先方から範囲拡大を求められた場合の落とし所は
「貴社および貴社が本システムの保守・改修を委託した者に対し」まで。
これなら競合サービスへの転用には使われない。

## 最大のリスク — 10番と6番の組み合わせ

**「全額前払い」＋「返金特約」＋「毎週ソースコード共有」が同時に成立すると、
入金後に返金請求を受けつつコードだけ残る形が作れてしまいます。**

全額前払いを受け入れたのは、資金リスクと与信リスクが下がることの対価として
350,000円を値引きしたためです。返金条件が広いとその前提が崩れます。
**契約書案を見る前に署名しないこと。**
