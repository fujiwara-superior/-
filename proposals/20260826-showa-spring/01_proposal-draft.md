## 2. 私たちの現状理解

いただいた内容から、現在の受注業務を次のように理解しています。認識に相違があればご指摘ください。

```
 ┌─────────────────────────────────────────────────────────────┐
 │ ① 受信                                                       │
 │   FAX（複合機／紙）      メール（本文べた書き／PDF／Excel添付）  │
 └───────────────┬─────────────────────────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ ② 内容の判読                        【仮説】1件 1〜3分         │
 │   ・どの得意先か  ・どの品番か  ・数量／単位  ・希望納期        │
 │   ・図面品か標準品か  ・変更／追加／キャンセルか               │
 └───────────────┬─────────────────────────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ ③ 特定・照合                        【仮説】1件 2〜6分         │

 │   先方品番   → サンエス品番／自社品目コード                     │

                 ▼

 │ ④ 基幹システムへ手入力              【仮説】1件 2〜5分         │

 └───────────────┬─────────────────────────────────────────────┘
                 ▼

 │ ⑤ 確認・返信                        【仮説】1件 1〜2分         │
 │   在庫／納期の回答、注文請書の返送                             │
```

**この理解の根拠**

- ①〜⑤の工程分解と所要時間は、ご記入いただいた「手入力」「月400〜500件」という記述と、同規模の製造業における一般的な受注業務からの`【仮説】`です。実測値は初回打ち合わせで確認させてください。

## 3. 課題の構造化

| # | 課題 | 発生箇所 | 事業へのインパクト | 放置した場合のリスク |
|---|---|---|---|---|
| **A** | 入力工数 | ④ | 月450件×手入力。担当者の時間が「転記」に消費される | 受注が増えるほど人を増やさざるを得ない。増員なしでは受注機会そのものを制限する |
| **B** | 入力ミス | ②③④ | 誤品番・誤数量・誤納期が生産指示まで流れる | 手戻り・特急対応・返品。ばねは1個から受注されるため、少量誤出荷でも段取り替えコストが重い |
| **C** | 属人化 | 全工程 | 処理・管理方法が担当者任せで共有されていない | **担当者の不在（病欠・退職）で受注業務が停止する。**引き継ぎに数ヶ月を要する。改善の議論もできない |
| **D** | 状況が見えない | 全工程 | どの注文がどこまで進んだか把握できない | 納期回答が遅れる／二重対応・対応漏れが起きる。問い合わせ対応が担当者に集中する |

**最も重いのは C です。** A（工数）は費用の問題ですが、C は**事業が止まるかどうか**の問題です。ご相談文で「属人化」に触れられている以上、ここを解かない提案には意味がないと考えています。

> **用語補足**
> **AI-OCR**：画像から文字を読み取る技術。従来のOCRに機械学習を組み合わせ、かすれや傾きに強くしたもの。

> **Human-in-the-Loop（HITL）**：処理の途中に人の確認を意図的に組み込む設計思想。

### 5-2. 実装上の重要論点

御社の業務特性を踏まえ、特に以下を設計の核とします。

#### (1) 精度の本丸は OCR ではなく「マスタ突合」です

これが本提案で最もお伝えしたい点です。

文字認識は必ず誤ります。特に品番では `0`と`O`、`1`と`I`と`l`、`8`と`B`、ハイフンの有無といった混同が起きます。**しかし御社には約1,717種のサンエス品番という確定した正解リストがあります。**

```
 OCR結果        「AP-1O-25」   ← O（オー）と誤認
      ↓
 品番マスタ照合  「AP-10-25」が存在／「AP-1O-25」は存在しない
      ↓
 自動補正        「AP-10-25」（確信度98%）
```

読み取り精度そのものを上げるより、**存在しない品番を機械的に弾く**ほうが確実です。得意先ごとの呼称（先方品番）についても読替表を整備すれば、同じ仕組みで吸収できます。

#### (2) 標準品と特注品を入口で分ける

御社の受注は性質の異なる2種類が混在していると理解しています。

| | 標準品（サンエス） | 特注品（図面・異形線ばね等） |
|---|---|---|
| 特徴 | 型番指定・リピート・在庫品 | 図面ベース・仕様確認が必要 |
| 判断の要否 | 少ない | 技術的判断が必須 |
| 自動化適性 | **高い** | 低い（自動化すべきでない） |
| 本提案での扱い | 自動起票の対象 | **見積依頼として技術担当へ自動振り分け** |

特注品を無理に自動化しません。むしろ「特注品を技術担当へ確実に、早く渡す」ことに価値があります。**振り分けの自動化だけでも、見積回答のリードタイムは短縮できます。**

#### (3) FAX と メールで処理を変える

| 入力形態 | 処理方式 | 精度の見込み `【仮説】` |
|---|---|---|
| Excel添付 | **OCRを通さず直接読む** | ほぼ100% |
| PDF（テキスト埋め込み） | **OCRを通さず直接読む** | ほぼ100% |
| PDF（スキャン画像） | AI-OCR | 高 |
| メール本文べた書き | 生成AIで直接抽出 | 高 |
| FAX（活字） | AI-OCR（前処理あり） | 中〜高 |
| FAX（手書き数量） | AI-OCR＋確認必須レーン | 中 |

**Excel・PDFをOCRに通すのは精度を捨てる行為です。**形式を判定して処理を分岐させます。FAXについては、傾き補正・ノイズ除去・解像度補完といった前処理を入れたうえで、手書き箇所は必ず人の確認に回す設計とします。

#### (4) 受注特有のパターンへの対応

一般的なOCR提案が取りこぼしがちな、実務上必ず起きるケースです。

- **重複注文**：同じ注文がFAXとメールの両方で届く／再送される → 得意先＋注文番号＋日付で自動検知し警告
- **変更・キャンセル**：既存受注への訂正 → 新規起票せず、該当受注を特定して差分を提示
- **分納指定**：1明細に複数納期 → 明細行を分割
- **希望納期の表記ゆれ**：「至急」「9月上旬」「9/10まで」→ 日付へ正規化。曖昧なものは確認レーンへ

### 5-3. 属人化（課題C）をどう解くか

工数削減とは独立して、必ず実装する要素です。

| 打ち手 | 内容 |
|---|---|
| **判断ルールの外出し** | 「この得意先のこの表記はこの品番」といった担当者の頭の中のルールを、**編集可能なマスタ**として system 上に置く。誰でも参照・更新できる形にする |
| **処理履歴の記録** | 誰が・いつ・何を修正したかを全件記録。「なぜこう入力したか」が後から追える |
| **進捗ダッシュボード** | 未処理／確認待ち／起票済を一覧化。担当者に聞かなくても状況が分かる |
| **修正パターンの蓄積** | 人がAIの結果を修正した内容を蓄積し、繰り返し発生する修正はルール化して自動補正に昇格させる |

**結果として得られるもの：** 担当者が不在でも、他の方が画面を見れば処理を継続できます。引き継ぎ資料ではなく、システムそのものが手順書になります。

### 7-3. この数字について、率直な見解

**工数削減だけを見れば、補助金なしの投資回収は決して速くありません。** 保守的シナリオでは7年を超えます。これを「3年で回収できます」と申し上げることはできません。

そのうえで、次の3点を合わせてご判断いただきたいと考えています。

1. **補助金の活用で回収期間はおよそ半分になります。** IT導入補助金等の対象となる可能性があります（次章）。
2. **課題C（属人化）の解消は、工数削減とは別の価値です。** 受注入力を担える方が1名しかいない状態は、金額に換算しにくいものの、事業継続上の明確なリスクです。「その方が3ヶ月不在になったら何が起きるか」を基準にご評価ください。
3. **受注件数が増えたとき、人を増やさずに対応できます。** 現状は月450件が担当者の処理能力に張り付いており、受注増がそのまま残業か機会損失に変わります。
